## 实现与验证

SQLite v4 保存快照的正文、身份、三库修订、SHA 和提交事件水位。首次执行在三库锁内读取一致版本，先提交 prepared 快照，再原子保存会话目录文件，最后将 committed 标记、注入统计和事件一起提交。提交后的快照禁止修改及删除。同会话后续任务和恢复读取原快照，新会话读取当前库；文件丢失、内容损坏或身份变化均明确返回结构化错误。准备事务期间取消会等待当前快照提交，启动恢复完成未提交意图。

首次员工执行通过现有 Provider 的 aux 槽，根据真实岗位生成配额 45%–55% 的 soul。保存完整生成请求、模型、事件、usage、结果和来源，写入复用三库账本。超出目标范围或者生成执行失败时明确终止，不保存不合格正文。真实生成约束的五次失败观察见 [generation-constraints.json](assets/M1/03/generation-constraints.json)，均未建立 soul 库或会话快照。

注入扫描统一保护快照和模型工具读取，识别中文、英文、全角字符、不可见字符以及工具和凭据泄露指令。正常审批纪律中的直接否定动作可以保留；重叠扫描继续检查同句后续动作。疑似注入在上下文中替换为 BLOCKED，磁盘保留原文。高风险材料在所有者审核之前排除，模型不能提交审核。审核保存所有者身份、时间和独立来源，保留原条目的来源与依据，仅新会话读取审核结果。

快照注入单独计数。显式命中通过 memory_usage 维护，不修改正文文件、metadata、业务修订或冻结快照。当前未提供 Skill 正文读取，M1-05 接入该使用口径。

针对性检查执行 **48 项通过**，覆盖快照与存储、迁移和启动，见 [snapshot-tests.txt](assets/M1/03/snapshot-tests.txt)。其中快照测试 **17 项通过**，包含范围隔离、状态表达、统计独立、审核边界、损坏拒绝、准备事务取消、攻击扫描和三个真实 SIGKILL 阶段。既有 SSE 回归使用真实监听 socket 的发送缓冲及真实慢消费者制造背压，核对溢出、关闭控制帧和重连补播，**9 项通过**，见 [sse-tests.txt](assets/M1/03/sse-tests.txt)。OpenAPI 检查通过，见 [openapi.txt](assets/M1/03/openapi.txt)。

## 真实模型与恢复

当前 main、aux 实际模型均为 `deepseek-v4.1-flash`。真实 aux 生成 **1328 字符**的 soul，占默认 2700 配额的 49%。四项 HTTP 任务全部 completed：首次任务 `2d60ffa249af4fddaaf8921a7fe0072c`，同会话后续任务 `eb9c3111484c45d2bc08f1b9b4c62661`，新会话任务 `67004c43e5164100ad8d70a66949bf65`，SIGKILL 恢复任务 `350ecfd849f54c1496f07a55ad78e168`。

记录六个真实模型 HTTP 请求，包括一次 aux 和五次 main。全部 main 请求包含完整 soul。原会话四次请求的冻结记忆块相同，修改后的项目代号和金额均未进入原会话；新会话读取新项目代号和已审核金额。未审核材料始终排除，投毒材料始终显示 BLOCKED。两份快照提交事件水位为 4、20，数据库正文、文件和实际请求相互一致。恢复请求中的副作用账本保持现有恢复规则，冻结记忆块及独立 SHA 保持不变。

真实服务先正常退出，再在模型请求开始后由父进程发送 SIGKILL，重启后通过实际 HTTP resume 继续完成任务。服务退出码依次为 0、-9、0，三条审计记录通过内部链及 chain-head.txt 锚点核验。任务、会话、模型请求、指纹、SQL、事件水位、文件 SHA 和 mtime 见 [http-model.json](assets/M1/03/http-model.json)。

另外使用三个真实子进程，分别在快照 prepared 提交后、文件原子替换后、最终事务提交后发送 SIGKILL，退出码均为 -9。各目录执行两次恢复后，同一快照身份和 SHA 保持不变，快照事件恰好一次；随后更新三库仍保持旧会话冻结。边界观察使用 Python profiler，未替换持久化实现。证据见 [sigkill.json](assets/M1/03/sigkill.json)。
