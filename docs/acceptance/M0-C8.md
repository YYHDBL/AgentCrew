## 0. 交付物清单

- **ReAct 主循环**（`agentcrew_core/loop/__init__.py`，纯编排：provider 流/工具执行/事件出口全注入）：
  - `run_task`：模型请求 → 有 tool_call 则 assistant tool_use 块先入历史（v1.9）→ 调度执行 → tool_result 块配对回填 → 下一轮；无 tool_call 写最终回复（messages 投影 + 事件全文）→ completed
  - 环境块注入 system prompt 尾部（v1.7）：`env_block`（日期时间星期/macOS/任务 cwd/资料目录/授权文件夹/工作区名），每次任务开始时刷新；provider `stream()` 新增 `system` 参数
  - **llm.request_done 载荷 = 回复全文 + 本次全部 tool_use 块（id/name/input）+ thinking 块（含 signature）+ stop_reason**——C9 恢复重建对话与结果配对的唯一依据（v1.7），逐字段对齐 projections.py 头部契约
  - 循环稳定性三招（§5 v1.5）：回合上限（gates.max_steps，超限 RUN_FAILED(max_steps)）；重复守门 `RepeatGate`（连续 3 次同 (tool,input_hash) 同结果 → 纠偏消息注入，再犯 RUN_FAILED(doom_loop)）；解析重试（坏 tool_use 流终态错误同上下文重采样，上限 2 → RUN_FAILED(unparseable)）；另：已产出事件后的可重试中断整轮重发上限 1 次，**重发前丢弃本轮部分输出**（C4 移交欠账）
  - token 预算硬上限（gates.token_budget，默认 2,000,000，超限 RUN_FAILED(token_budget)；压缩是 M1 不做）
  - **终态时序契约（v1.7）**：模型流显式 `aclose()`（①）+ 工具批 `asyncio.TaskGroup` 全收割（②，bash 进程组杀+wait 是 C5 既有行为）之后 run_task 才返回，RUN_COMPLETED/FAILED 由 RunManager 在返回后发射；dispatched 无结果的调用其账本行已随 tool.dispatched 事件持久化（③，C9 对账域）
  - thinking 保守姿态：多轮历史按 thinking_block 事件携带的 signature 回传 thinking 块（欠账）
- **RunManager**（`agentcrew_server/run_manager/__init__.py`）：
  - 每 TaskRun 一个 asyncio 任务 + 注册表；总线 internal 订阅（不占 SSE 32 连接名额）监听 run.queued/run.resumed 派发 runner——四个入口（创建会话/直发指令/queue.continue/终态自动接续）统一走这一条派发路径
  - 全局并发 8 FIFO（gates.global_concurrency，信号量；等待名额期间 FSM 停 starting 可被取消）
  - **配置版本绑定（v1.7）**：每次 attempt 开始快照 models/gates/system prompt/tools schema → `context_fingerprint{system_prompt_hash, tools_schema_hash, model_config}` 随 run.started 载荷落 run_attempts；模型槽经独立 Provider 实例绑定（共享 httpx 连接池）——运行中 PATCH settings 不影响本任务，下一新任务用新版
  - 取消传播：task.cancel() 打到模型流（aclose）、工具子进程（C5 杀组）、ask_user 等待（注册表就地清理，库中留下未回答状态）；用户停止 → run.cancelled + 队列非空补发 queue.paused（§4 不自动接续）；优雅关闭 → 取消但不写终态（§6，C9 对账收敛）
  - 停滞看门狗：模型 delta/工具完成/审批与提问决定刷新 last_progress（bus 订阅 permission.*/question.* 事件维护等待计数）；等待用户期间不计时；超阈值 → RUN_FAILED(stalled)
  - 接续规则（v1.4）：completed/failed → `sessions.auto_dequeue_next`（同会话锁内重读 FSM，竞态让位）；**failed 注入护栏提示**（"上一条指令已失败（原因…），请确认是否仍需要执行本条指令"——before_publish 回调在事件发布前挂上，杜绝派发竞态）；cancelled → 不接续
  - 同会话上下文连续：新任务上下文 = 已完成任务（指令 + 最终回复）对 + 新指令（失败/取消任务不进上下文，由护栏显式化）
- **ask_user 全链（S07）**：`QuestionService`（`questions.py`）——resolver 独立生命周期（不走调度器：无 60s 工具超时、不占 4 并发位；账本三事件 prepared/dispatched/completed 照发）；`POST /api/questions/:requestId/answer`（answer=null 按"拒绝回答"告知模型；live future 跨线程唤醒，answered 事件由 _ask_user 单一来源发射；重启后孤儿提问由 submit 直接落事件留事实）；`GET /conversations/:id/questions`（仅活跃任务的未回答提问）

## 3. 三笔欠账清账

1. **S07（ask_user 独立生命周期）**：ask_user 在循环执行器直通执行（不走调度器——无 60s 超时、不占并发名额），账本三事件照发；任务取消时 resolver 就地清理注册表、库中留下 question.requested 无 answered 的未回答状态、tool_calls 停 dispatched（C9 对账域）。C 场景 65s 等待 + F 场景取消留痕实证。
2. **C4 移交（已产出事件后的中断）**：适配层上交 error(retryable=true) 后循环层决定整轮重发（上限 1，对齐 C4 卡"可重试一次续跑"），**重发前丢弃本轮已收到的部分输出**（每次尝试从空白缓冲开始，messages 不受污染）；丢弃回合只留 llm.request_failed 事件事实。
3. **thinking 保守姿态**：多轮历史按 thinking_block 事件的 signature 回传 thinking 块（assistant content 首块），llm.request_done 载荷同步持久化 thinking 块供 C9 精确重建。

## 4. 与设计的偏差及理由

1. **流式打字 delta 帧未上 SSE**：事件契约（events.md v1.1）无 delta 帧类型，且 SSE 去重按 global_seq（delta 帧无游标）；C8 卡验收只要里程碑 STEP/LLM/TOOL 事件。按纪律"新增机制先加帧类型"，留待 C11 需要打字效果时补契约再实现。
2. **解析重试的口径**：C4 适配层把坏 tool_use 参数归一为流终态 error（UNKNOWN 类），循环层拿不到 call_id，无法按 §5 原文"以错误 tool_result 回填"——实现为同上下文重采样（上限 2 → unparseable）。工具参数 schema 级错误（如缺 path）仍自然走 tool_result 错误回填通道让模型自纠。
3. **丢弃 vs 后缀保留**：设计 §5"重试的原始坏响应用后缀标记保留"与 C4 移交"必须先丢弃上一轮部分输出"冲突，按移交欠账执行丢弃（不污染对话历史，事件流留 llm.request_failed 事实）。
4. **同会话上下文连续的实现边界**：新任务上下文含已完成任务的（指令 + 最终回复）对；失败/取消任务不进上下文（避免模型重试已取消指令），由 failed 接续的护栏提示显式化。
5. **run.cancelled 与 queue.paused 成对发射**：C7 演示已确立（reducer 语义的持久化投影），C8 落实为 runner 行为——队列非空时用户停止补发 queue.paused 事件。
6. **跨卡小交付**：`GET /conversations/:id/task-runs` 与 `GET /task-runs/:id/attempts` 属契约 §10"运行记录"簇（无卡认领），attempts 是 fingerprint 验收面，随本卡交付。
7. **gate 相对路径修复**（C5/C6 缝隙，见交付物清单末条）：审批 target / 规则 pattern 以任务 cwd 解析——不修则相对路径写入的 allow_always 规则指向进程 cwd，同类放行永不生效（B 场景 e.md 依赖此修复）。

## 5. 已知天花板（ponytail 标注）

- 看门狗在等待审批/提问期间重置计时窗（等用户时不计时）；若用户在审批卡上放置极久后决定，之后停滞窗口从决定时刻重新起算——符合"滑动窗口"语义。
- 全局并发等待名额的任务停在 starting 相位、看门狗未启动（进展计时从 run.started 起）——等待名额本身不算停滞。
- failed 接续的护栏提示存内存注册表：接续瞬间崩溃则护栏丢失（任务照跑，仅少一句提示；v1.7"护栏只是显式化"）。
